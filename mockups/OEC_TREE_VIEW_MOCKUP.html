OEC System View — Evaluation & Enhancement Options

Option 7 · OecPanel "Data" tab (gui/panels/catalogs.py::_oec_tree_item) · mockups only, nothing implemented · 2026-08-01

What the view does today

A two-column QTreeWidget: column 0 is the node name (icon + name + spectral type or status badges), column 1 is a single string of space-joined label=value unit fragments built from a fixed per-tag key list (_OEC_TREE_KEYS). Everything is expanded on load and nothing is sortable, selectable-for-detail, or copyable as data.

Assessment

Works well
  • The hierarchy is the right primary encoding — OEC really is recursive, and the tree makes binary → binary → star → planet legible at a glance.
  • Icon prefixes (◆ ⋔ ★ ● ☾) read fast; the M·sin i relabel and multi-status badges are correct and non-obvious wins.
  • The generic node walker already captures every field in the XML — the shortfall is purely presentational, so all options below are display-layer work with zero core changes.
Limits
  • One string, no columns. Values can't align, sort, or be scanned down a column; long rows truncate at the panel edge and the whole per-node payload is lost.
  • Fixed 4–6 keys per tag. Everything else the parser captured is invisible in this tab — including planet description (93% coverage) and every satellite orbital element.
  • No drill-down. Clicking a node does nothing; the only rich per-planet view is the Architecture map's click dialog, which is unreachable from the Data tab.
  • Errors inflate the cell. +0.0041/-0.0051 inline triples the width of every measured value and buries the number it qualifies.
  • No units toggle. Planet mass/radius are M♃/R♃ only; a 0.0037 M♃ planet is unreadable where 1.17 M⊕ is not.
  • Nothing derived. Distance is pc-only (no ly), no density, no insolation, no HZ verdict — though the app computes all of these elsewhere.

★ Recommended View — Option B, star-first

Option B's master/detail split, with three changes that answer "more detail about the stars in view": the tree rows carry the star's key numbers in the same columns as the planets (Option A); the detail pane is a full star dossier when a star is selected; and when a planet is selected the host star stays pinned as a context band at the top of the pane, so you never lose the star while reading its planets. Toolbar from F, derived values from G.

Why this composition
  • Star data is never behind a click. The tree columns carry M, R, Teff, derived L and the HZ bounds on the star row itself, so a glance at the system already tells you what kind of star it is.
  • The pane is the only place ~50 fields can live. Photometry alone is eight fields and three derived colours; there is no column budget for that anywhere else.
  • The pinned band solves the real complaint — in a plain master/detail, selecting a planet makes the star vanish. Pinning keeps L, HZ and snow line on screen exactly when you are judging a planet against them.
  • Derived is always violet + badged, so a computed luminosity is never mistaken for a catalogued one, and one checkbox removes the whole class.
  • Reuses what exists: the planet click-dialog becomes the pane's planet mode; HZ / evolution / RV / transit numbers all come from functions already in core/.
Build order
  1. Columnar tree + star rows populated (Option A) — biggest visible gain, smallest change.
  2. Detail pane skeleton with per-tag section tables; planet mode wired to the existing dialog content.
  3. Star dossier blocks: identity, position, photometry, physical.
  4. Derived layer (luminosity → HZ → insolation → the rest) behind one toggle.
  5. Pinned host band + Companions block from the parent binary.
  6. Toolbar: units, errors, hide-empty, copy/export.

All display-layer. The node walker already carries every field used above; no core change is required except calling existing calculators for the derived block.

Option A · Columnar Tree

Keep the tree exactly as it is structurally; replace the single crammed properties string with real aligned columns. Errors move to a subscript so the value stays scannable. Numbers are right-aligned so magnitudes compare down the column. Columns are per-tag-polymorphic — a star's "M" is M☉, a planet's is M♃/M⊕, and the header adapts to the selected unit system.

Field gain per node type
  • system → + RA, Dec, distance in ly beside pc, planet count, star count
  • binary → + position angle, periastron, ascending node, both separation forms
  • star → + magV, magB, magK, B−V (derived), age, luminosity (derived)
  • planet → + Teq, discovery method & year, transiting badge, last update
  • satellite → + e, i, periastron, ascending node, tilt (all at 100% coverage)
Design notes
  • Status moves from a bracket in the name to compact Conf / Cand / S-type badges — the name column stops being 90 characters wide.
  • Errors render as a dimmed suffix at ~85% size: present but visually subordinate. A checkbox drops them entirely for a clean scan.
  • Columns irrelevant to a node stay blank rather than showing — if you prefer; "Hide empty columns" removes a column no visible node populates (a single-star system loses the binary-only columns automatically).
  • QTreeWidget supports sortable columns natively — but sorting a hierarchy sorts within each parent, which is exactly right for planets under a host.
Trade-off. Ten columns is roughly the panel's width budget. This option makes the top ~10 fields excellent and leaves the other ~40 still hidden — which is why it pairs naturally with B or F.

Option B · Tree + Detail Pane (master/detail)

The tree becomes a navigator. Selecting any node — system, binary, star, planet or moon — fills a right-hand pane with every field the parser captured for that node, grouped into sections, with full uncertainties, units, bound markers, all alias names, and a derived block. Nothing is ever dropped because it wouldn't fit.

Description

Astronomers using ESO telescopes and other facilities have found clear evidence of a planet orbiting the closest star to Earth, Proxima Centauri. The long-sought world, designated Proxima b, orbits its cool red parent star every 11 days and has a temperature suitable for liquid water to exist on its surface…

Why this is the strongest completeness answer
  • The pane is scrollable, so field count is unbounded — the long tail (impact parameter, mean anomaly, tilt, position angle) shows when present and silently disappears when not.
  • It is the only option that can show all alias names — α Cen A carries 22 of them, all currently invisible.
  • Bound-only values (e ≤ 0.35) and asymmetric errors get room to be honest instead of being truncated.
  • "— not in catalogue" vs. "— not measured (non-transiting)" distinguishes absent data from physically unmeasurable. The tree can't make that distinction in a cell.
  • Reuses the existing planet click-dialog content — the dialog becomes an embedded pane that also works for stars, binaries and moons.
Costs / decisions
  • Halves the tree's horizontal room — mitigated by the Right/Below/Hidden toggle (Below suits wide-and-shallow systems, Right suits deep hierarchies).
  • Needs a per-tag field ordering + label table (~50 entries) and a "known keys first, then everything else alphabetically" fallback so a future OEC field never goes missing.
  • The derived block needs a clear visual mark — the computed badge and violet tint — so a computed insolation is never mistaken for a catalogue value.

Option C · Tree Navigator + Per-Tier Tables

Keep the tree small at the top as a structure map, and put the data in flat, sortable, full-width tables — one per tier. This is the shape every other Star-Databases panel already uses (opts 1–6), so it inherits their conventions: dense columns, right-aligned numbers, copyable rows. A system's whole planet inventory becomes one sortable table regardless of how deep in the hierarchy each planet hangs — with an "Attached to" column preserving the topology.

Strengths
  • Sortable and copyable — click "P (d)" to order a 8-planet system by period; select rows and paste into a spreadsheet. Neither is possible in the tree today.
  • Column budget is ~16 instead of ~10, and each tier gets columns tuned to it rather than a lowest-common-denominator set.
  • Consistent with HWC / NASA / Mission-Exocat panels — the user already knows how to read it.
  • The moons tier finally has somewhere to show all ten of its 100%-coverage fields.
Weaknesses
  • Flattening loses the visual hierarchy — mitigated by the "Attached to" column and the retained Structure sub-tab, but a deep α Cen-style nesting reads worse than in a tree.
  • Five sub-tabs on top of the existing Data / Hypatia tabs is a lot of chrome; the empty tiers (Moons 0) should hide themselves.
  • Still no home for description — needs D, or a detail row expander.

Option D · Dossier Cards

A reading view rather than a data view. The system gets a header block, each star a compact card, each planet a full card carrying the fields plus the description prose that 93% of planets have and that nothing in the app currently shows. Badges encode status, method and transiting-ness. This is the view that answers "tell me about this system" rather than "give me the numbers".

Cheapest useful subset of D: keep the tree, and add a description expander row under each planet node (a wrapped grey italic child row, collapsed by default). That single change surfaces the biggest missing field with no new view.

Option E · Planet Comparison Matrix

Transposed: properties down the rows, planets across the columns — the same shape StarComparisonPanel (Phase L1) already uses for stars. For a multi-planet system this is the fastest way to see how planets differ, and it can carry the full property list because rows are cheap. Blank cells make catalogue gaps immediately visible as a pattern.

Illustrative values for layout review.

Strengths
  • Row count is unconstrained — every planet field can appear, including the long tail, because adding a property costs one row not one column.
  • Gaps become a visible pattern: an all-blank "Radius" row instantly says "this is an RV system".
  • Reuses the L1 transposed-table idiom already in the codebase, and the Solar-System reference column mirrors the O4 orbital-diagram overlay.
Weaknesses
  • Per-host only — needs the Host combo, and says nothing about multi-star topology. Useless for a single-planet system.
  • Wide systems (Kepler-90, 8 planets + reference) push against the panel width.
  • Complements rather than replaces: it is a third view, not a new default.

Option F · Toolbar / Control Layer

Not a view — the controls that make A or C work at both extremes (a bare 1-planet RV detection and a fully-characterised 8-planet transit system). Each control is independently useful and independently cheap; they can be adopted one at a time.

Units M⊕ / R⊕M♃ / R♃SI Density CompactComfortable Hide empty columns Errors Derived
Unit toggle high value

OEC stores planet mass/radius in Jupiter units. For the terrestrial planets that dominate the catalogue this is unreadable — Proxima b is 0.003691 M♃, i.e. 1.17 M⊕. The conversion already exists in catalogs.py (_MJUP_MEARTH / _RJUP_REARTH) for the diagram adapter; this exposes it in the tables. Suggested default: auto — M⊕ below 0.1 M♃, M♃ above.

Hide empty columns / rows high value

Coverage is wildly uneven (mass 52%, radius 77%, inclination 32%). Dropping columns no visible node populates recovers 30–50% of the width on a typical system, which is what makes a 10–16 column layout viable at all.

Errors on/off

Uncertainty is essential for research use and pure noise for scanning. Three states are worth having: off, inline dimmed (default), and own column (± as separate sortable columns, for the tier tables in C).

Column chooser

A checklist per node type over all captured field names, so a rare field (spin–orbit alignment, impact parameter) is reachable without a code change and without being on screen by default. Persist the choice per node type in QSettings.

Filter box

Type b or transit to prune the tree to matching nodes and their ancestors. Mostly matters for large systems and for the Structure tab in C.

Copy / export high value

Nothing in the Data tab is currently extractable. Copy-TSV of the selection and Export-CSV of the tier follows the existing opt-51 export idiom, and is the cheapest of all these controls to build.

Expand-state default. Today the tree calls expandAll() unconditionally. For α Cen that is right; for a 8-planet system with binary nesting it overflows the 360 px minimum height immediately. Suggested rule: expand all when the node count ≤ 25, otherwise expand to the star level and leave planets collapsed — with the Expand/Collapse button always available.

Rules this should follow
  • Never merge into the catalogue block. Derived values get their own section (B), their own column tint (A/C/E) or an explicit badge (D). A derived Teq and a catalogued Teq must be distinguishable at a glance.
  • Prefer the catalogued value when both exist, and offer the derived one beside it as a cross-check — a disagreement is itself informative.
  • Say what is missing. "— (no radius)" beats a blank cell: it tells the user the calculation was attempted and why it failed.
  • One toggle kills them all (F's "Derived" checkbox) for anyone who wants the raw catalogue and nothing else.
Cheapest high-value subset
  1. Distance in ly (one multiplication, 95% coverage)
  2. Star luminosity + HZ bounds (existing calls, 83% coverage)
  3. Planet insolation + HZ verdict (depends on 2, 52% coverage)
  4. Density + surface gravity (arithmetic, ~45% coverage)
  5. Equilibrium T where OEC has none (fills 70% of the gap)

Those five cover the questions a reader actually asks of a system and need no new core code at all.

Recommendation

Build the ★ Recommended view — Option B's master/detail split, star-first: the tree gains Option A's columns with the star rows populated (M, R, Teff, derived L, HZ bounds), the detail pane becomes a full star dossier (all aliases, RA/Dec, all eight magnitudes + colours, physical + evolutionary state, HZ and ice lines, hosted-planet inventory, companion orbit), and the host star stays pinned as a context band while you read its planets. Option F's toolbar (units, errors, hide-empty, copy/export) and Option G's derived layer ride along behind toggles.

It is entirely display-layer work: the node walker already captures every field shown, and every derived value comes from a function already in core/.

Still worth taking separately: D's description expander (one collapsed child row per planet surfaces the 93%-covered description for almost nothing), and C or E as extra tabs later if sorting and side-by-side comparison turn out to matter more than hierarchy.
