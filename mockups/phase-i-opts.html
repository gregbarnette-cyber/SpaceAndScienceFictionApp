Proposed Additions — Overview

Each candidate answers a routing question the current three (I1–I3) cannot. They are all GUI-only, pure-core, self-validating (the Phase I/H {"error": str} contract), and reuse the existing Star Chart routes= overlay. Pick the ones you want and I'll write specs + build them.

What each one is for

CandidateLogicQuestion it answersGap it fills
A · Optimal TourNearest-neighbor seed + 2-opt local search; open or closed loop "Visit all these stars in the order with the shortest total trip" I2 is greedy & never backtracks — its total route is often far from optimal
B · Jump-Range PathfindingDijkstra (min distance) / BFS (min jumps) over a jump-limited graph "Get from A to B through intermediate stars, each jump ≤ my drive's range" Point-to-point navigation with a hard jump range — nothing covers this today
C · Jump Network / ReachabilityBFS frontier — min jumps to every reachable star "At jump range X, what can I reach from here, and in how many jumps?" Empire-frontier / expansion mapping — strategic, not a single route
D · Farthest-First CoverageGreedy farthest-from-visited traversal (de-clustering) "Plant N outposts spread as widely as possible" Direct counterpoint to I2's clustering (your Alpha Cen result)

Optimal Tour Planner CANDIDATE A

Visit a given set of stars in the order that minimizes total trip distance — the fix for nearest-neighbor's greediness. The first line is the fixed start; tick Closed loop to return to it.

Proposed plan details
  • Proposed compute_optimal_tour(star_names, velocity_input, use_times_c, closed=False) — self-validating, GUI-only.
  • Resolve + case-insensitive dedup (like I3). Nearest-neighbor seed from the first stop, then 2-opt reversal passes until no improvement.
  • First node stays fixed (the entered start); 2-opt reorders the rest. Open tour = end free; closed = return-to-start leg added.
  • Why: I2 minimizes each hop, not the trip. For the handful of stars a worldbuilder picks, 2-opt reaches near-optimal instantly.
  • Reuses I1's leg / format_travel_time math + the dashed routes= overlay.

Jump-Range Pathfinding CANDIDATE B

Navigate from an origin to a destination through intermediate stars, where every single jump must be within the drive's max range. Minimize total distance travelled, or the number of jumps.

Proposed plan details
  • Proposed compute_jump_route(origin, destination, max_jump_ly, optimize="distance"|"jumps") — self-validating, GUI-only.
  • Build an implicit graph over star_systems: an edge connects any two stars within max_jump_ly. Dijkstra (distance) or BFS (fewest jumps) from origin to destination.
  • No path within range → reachable=False (a clear message, not a crash) — the map shows the disconnected endpoints over the faint jump lattice.
  • Why: a jump drive with a hard per-jump range is a core FTL trope; I2 wanders with no destination — this is true point-to-point navigation.
  • Reuses the pool loader + dashed routes= overlay; faint lines show the reachable lattice for context.

Jump Network / Reachability Map CANDIDATE C

From a start system, with a given jump range, map everything reachable and how many jumps away it is — the connected "empire frontier."

Proposed plan details
  • Proposed compute_jump_network(start, max_jump_ly, max_jumps=None) — self-validating, GUI-only.
  • BFS over the same jump-range graph as B, labelling each reachable star with its minimum jump count (tier). Stars outside the connected component are listed as unreachable-nearby.
  • Why: answers expansion / strategic questions ("how far does my territory extend at range X; which systems are 1/2/3 jumps out") that no single-route planner touches.
  • Reuses the I2 pool; the Star Chart colours nodes by jump tier instead of spectral class.

Farthest-First Coverage Chain CANDIDATE D

Explore for maximum spread: each step picks the unvisited star farthest from everything already visited (optionally still within reach of the chain). The de-clustering sibling of nearest-neighbor.

Proposed plan details
  • Proposed compute_farthest_first_chain(start, num_stops, max_reach_ly=None) — self-validating, GUI-only.
  • Greedy farthest-from-visited: track each candidate's distance to the nearest visited star; repeatedly pick the one that maximizes it (so the set spreads out). With a reach limit, a pick must be within max_reach_ly of some visited star — else the chain ends early.
  • The dashed edges form the exploration tree: each new star links to the nearest visited star it reached from.
  • Why: I2 hugs dense multiples (Proxima → α Cen A → α Cen B). This is the opposite intent — cover ground, not stars.
  • Shares almost all of I2's scaffold — same loop, selection criterion flipped.
