# PHASE S — Project Workspaces (Campaign / Novel Manager) · Analysis + Mockup

> **This is the analysis + mockup gate for S — design only, NO code.** Companion to
> [`PHASE_S_MOCKUP.html`](../mockups/PHASE_S_MOCKUP.html) (panel layout). The numbered, build-ready
> `PHASE_S_PLAN.md` is the **next** gate and is written only after this mockup is signed off
> (house rule: no code until the plan is approved).
>
> **Builds on Q (shipped 2026-06-20) + R (R1/R2/R3, complete 2026-06-24).** S is the last planned
> forward-looking phase. It turns the app from a per-system analysis tool into a lightweight
> **worldbuilding workspace**: named projects that collect curated real + procedurally-generated
> systems with notes, and export the whole set as one document. It **reuses** Q's dossier composer
> and R's generator verbatim — the only genuinely new design question is how a *generated* member is
> persisted and reproduced (§4). See `future_phases.md` (Phase S brainstorm), `PHASE_Q_PLAN.md`
> (dossier), `PHASE_R_PLAN.md`/`PHASE_R3_PLAN.md` (generator). Phase **J** (a flat global favorites
> list) was **declined** — S is the standalone, project-scoped home that supersedes that idea.

---

## 0. What S is (one paragraph)

Every other phase answers a question about **one** system. **S is the first phase about a
*collection*.** A worldbuilder works in named projects — *"my novel,"* *"the Frontier campaign,"*
*"the Local Bubble setting"* — each a curated set of systems (real ones looked up via SIMBAD, and
procedural ones generated by R) with freeform per-system notes. S persists those projects in two
small additive SQLite tables, exposes CRUD through a new pure `core/projects.py`, surfaces a
master-detail **`ProjectPanel`** (project list + member table with inline notes + per-row Open), and
**exports a whole project as one multi-system dossier** by fanning Q's `build_system_dossier` over
the members. A generated member stores its **generation spec** (seed + params), so it re-creates
**byte-identically** on demand without persisting its full body — the R determinism contract carried
into the workspace. Mutations are GUI-only; `query.py` gets read-only `project-list` / `project-get`
so the sibling repo can drive a whole setting. No existing behaviour changes.

## 1. Scope — in S vs. deferred

| In S | Deferred |
|---|---|
| Two additive tables (`projects`, `project_members`) via the idempotent `_migrate_schema` (existing DBs pick them up) | A relational system/planet store — members reference a star **name** + (for generated) a **spec**, not a denormalised body |
| `core/projects.py` — self-validating CRUD (`create`/`list`/`get`/`add_member`/`update_note`/`remove_member`/`rename`/`delete`) | Sharing/sync/multi-user; cloud storage |
| **`ProjectPanel`** (new "Projects" nav category) — master-detail, inline note editing, per-row Open, Export | Drag-reorder, tags/folders, rich-text notes (plain-text notes only) |
| **"Add to project"** entry points on `SimbadPanel` (real star) + `SystemGeneratorPanel` (generated system) | Bulk "add all search results" (a thin follow-on; single-add ships first) |
| **Export Project Dossier** → Q batch over members (real → `build_system_dossier(name)`; generated → the R→Q **generated-system dossier**, §5) | Per-section export config UI beyond Q's existing `--sections` |
| The **generated-system dossier** render path (the long-deferred R→Q "Send to Dossier" link, §5) | Editing a stored spec in place (re-add to change it) |
| `query.py` read-only `project-list` / `project-get --name` | DB-write subcommands (mutations stay GUI-only — the "no DB-write subcommands" principle) |
| `DbStatusPanel` rows for `projects` / `project_members` | — |

**Hard rules:**
1. **No existing behaviour changes.** New tables are additive + not auto-seeded; new nav category +
   two additive buttons on existing panels; no edits to any existing core compute path. The full
   suite stays green untouched.
2. **Generated members reproduce byte-identically** from their stored spec (the R determinism
   contract — same seed + params → deep-equal). The DB stores the *spec*, never a frozen body that
   could drift from the generator.
3. **Mutations are GUI-only.** `query.py` is read-only over projects (writes belong to the
   interactive workspace), consistent with every other phase.

## 3. Data model — `core/db.py` tables + `core/projects.py` API

### 3a. Tables (additive; `_migrate_schema`, not auto-seeded)

```sql
CREATE TABLE IF NOT EXISTS projects (
    project_id   INTEGER PRIMARY KEY,
    name         TEXT UNIQUE NOT NULL,
    description  TEXT,
    created_date TEXT
);
CREATE TABLE IF NOT EXISTS project_members (
    project_id     INTEGER NOT NULL,
    star_name      TEXT NOT NULL,          -- display key + the dossier lookup key (real members)
    note           TEXT,
    source         TEXT NOT NULL,          -- 'looked_up' | 'generated'
    generated_seed INTEGER,                -- non-null for generated members
    generated_spec TEXT,                   -- JSON: the full generate_system params (§4) — generated only
    added_date     TEXT,
    PRIMARY KEY (project_id, star_name)
);
-- index on project_id for the member fetch.
```

> **Deviation from the brainstorm (§4):** the brainstorm stored only `generated_seed INTEGER`. A bare
> seed does **not** reproduce a specific generated system (a no-arg `generate_system(seed)` *samples*
> class + count, and constraints/anchor/policy change the output entirely). So S adds a
> `generated_spec` **JSON blob** (seed + mode + spectral_class + n_planets + anchor + constraints +
> companion + research_policy) — the minimal faithful-reproduction record. `generated_seed` is kept
> as a denormalised convenience/display column. **Open as D1.**

### 3b. `core/projects.py` (pure, self-validating, no Qt/network)

| Function | Returns / contract |
|---|---|
| `create_project(name, description="")` | `{project_id, name, …}` or `{"error"}` (blank/duplicate name) |
| `list_projects()` | `[{project_id, name, description, created_date, member_count}]` (sorted by name) |
| `get_project(name)` | `{project: {...}, members: [{star_name, note, source, generated_seed, generated_spec, added_date}]}` or `{"error"}` (unknown) |
| `add_member(name, star_name, note="", source="looked_up", seed=None, spec=None)` | idempotent `INSERT OR REPLACE`; `{"error"}` on unknown project / blank star |
| `update_note(name, star_name, note)` | `{"error"}` on unknown project/member |
| `remove_member(name, star_name)` | idempotent |
| `rename_project(old, new)` | `{"error"}` on unknown/duplicate |
| `delete_project(name)` | cascades to `project_members` (one transaction) |

All self-validating (Phase-H contract: curated `{"error": str}`). DB-isolation in tests via the
`core.db._DB_PATH` tmp-swap pattern (like `test_db_backups.py`).

## 4. The reproducibility model for generated members (the key design point)

A real member is just a name → `build_system_dossier(name)` re-derives it live. A **generated**
member must reproduce **exactly** what the user saw when they added it — R's headline determinism
contract. The DB stores its **spec**, not its body:

```jsonc
// project_members.generated_spec (JSON)
{ "seed": 88, "mode": "synthetic", "spectral_class": "K2V", "n_planets": 6,
  "anchor_star": null, "constraints": null, "companion": null, "research_policy": "permissive" }
```

Opening / exporting a generated member re-runs `generate_system(**spec)` → **deep-equal** to the
original (the R1/R2/R3 determinism tests already guarantee this). Benefits: tiny storage, never
drifts from the generator, and a `research_policy:"strict"` member faithfully records that it needs
an ingested dataset (and surfaces R3's curated error honestly if none is loaded).

- **`star_name` for a generated member** = the generator's `star["name"]` (e.g. `"Gen-88"` synthetic
  / the anchor's name for real-anchor), used as the display + PK. A name collision within a project
  (two `Gen-88`s) is resolved at add time with a suffix (`"Gen-88 (2)"`) — **D2**.
- **Anchored generated members** (`anchor_star` set) re-run with network (SIMBAD/NASA/HWC), like any
  R real-anchor generation; synthetic members are fully offline.

## 5. Export — Project Dossier (the R→Q link, incl. the deferred "Send to Dossier")

**Export Project Dossier** fans Q over the members and concatenates into one document:
- **Real member** → `build_system_dossier(star_name, sections, fmt)` (verbatim Q).
- **Generated member** → a **new additive `core/report.py` path** that renders a
  `generate_system` result dict as a dossier section (identity + star props + the generated planet
  table + the Source/grounding provenance). This is the long-deferred **R→Q "Send to Dossier"**
  handoff, finally built here because S is where a generated system needs a writeup. Signature
  sketch: `build_generated_dossier(result, sections=None, fmt="markdown")` — pure composition over
  the already-present generated dict, **no re-analysis**.
- The project doc = a title/description header + one section per member (in member order), in
  `markdown` / `html` / `json` (same three Q formats). GUI export writes one combined file (or, like
  Q's batch, one file per member — **D3**).

This keeps Q's contract intact (its `--star`/name path is unchanged) and adds the generated path as a
**sibling** composer, not a modification.

## 6. GUI — `ProjectPanel` + entry points

New **"Projects"** nav category (top-level, near "Reports"); `gui/panels/projects.py`.

- **Master-detail layout:** left = the **project list** (create / rename / delete; shows
  member-count); right = the selected project's **member table** — *Star · Note · Source
  (looked-up / generated seed N) · Added* — with inline **note editing** (double-click a Note cell),
  per-row **Open** (real → embed a `SimbadPanel`; generated → re-run `generate_system(spec)` and show
  it in an embedded `SystemGeneratorPanel`/result), and **Remove**.
- **Export Project Dossier** button → a small dialog (format + Q `--sections` + combined-vs-per-file)
  → the §5 fan-out on a background thread (real members hit the network; generated synthetic ones
  don't).
- **Entry points on existing panels (additive, ≤1 button each):**
  - `SimbadPanel` gains **"Add to project ▾"** (pick/-create a project → `add_member(source="looked_up")`).
  - `SystemGeneratorPanel` gains **"Add to project ▾"** (stores the current generation **spec** →
    `add_member(source="generated", seed=…, spec=…)`).
  Both are guarded so the panels are unchanged until clicked; no behavioural change to existing flows.
- `DbStatusPanel` (opt 57) appends **Projects** / **Project Members** rows.

See `mockups/PHASE_S_MOCKUP.html` for the master-detail layout + the Add-to-project menu + the export dialog.

## 7. `query.py` — read-only project readers

Two read-only subcommands (mutations stay GUI-only):
- **`project-list`** → `core.projects.list_projects()` → `[{name, description, member_count, created_date}]`.
- **`project-get --name <name>`** → `core.projects.get_project(name)` → `{project, members[]}` (each
  member's `generated_spec` echoed as parsed JSON), or `{"error"}` exit 1 for an unknown project.

So the sibling repo can enumerate a setting and pull each member (then call the existing
`dossier`/`generate-system`/`simbad-lookup` subcommands per member). No `project-export` subcommand
in S — the export composition is GUI-driven (it spans network + offline members); a headless
`project-dossier` reader is an additive later add if the consumer asks (**D4**).

---

## 8. Determinism & validation contract

- **Determinism:** a generated member re-creates **deep-equal** from its stored spec (the R contract;
  a new test pins add→get→`generate_system(spec)` == the original). `created_date`/`added_date` are
  provenance timestamps (not part of any reproduced body), like the GCNS `snapshot_date`.
- **Validation (self-validating — Phase H):** blank/duplicate project name, unknown project/member,
  blank star → curated `{"error"}`. Membership is idempotent (`INSERT OR REPLACE`). `delete_project`
  cascades in one transaction. `project-get` unknown name → exit 1; argparse exit 2 for a missing
  `--name`.

## 9. Decisions to resolve before `PHASE_S_PLAN.md`

| # | Question | Proposed default |
|---|---|---|
| D1 | **Generated-member persistence** — bare `generated_seed` (brainstorm) vs a `generated_spec` JSON blob (seed + all params)? | **`generated_spec` JSON** (+ keep `generated_seed` as a display column) — a bare seed can't reproduce a specific system (class/count are sampled; constraints/anchor/policy change everything). Faithful reproduction is the whole point. |
| D2 | **Member key / name collisions** — `star_name` is the PK within a project; two generated `Gen-88`s collide. | **Suffix on add** (`"Gen-88 (2)"`) — keeps a human-readable PK; the spec (not the name) carries reproduction. |
| D3 | **Export shape** — one combined project document, or Q-batch one-file-per-member? | **Offer both** (a radio in the export dialog); default **combined** (the "export the set as one dossier" headline). |
| D4 | **`query.py` export** — ship a headless `project-dossier` now, or only `project-list`/`project-get`? | **Only the two readers** in S; add `project-dossier` later if the consumer asks (the export spans network+offline members — GUI-first). |
| D5 | **"Add to project" reach** — just `SimbadPanel` + `SystemGeneratorPanel`, or also HWC/NASA/GCNS panels? | **The two named** in S (the primary real + generated sources); other panels are thin additive follow-ons. |
| D6 | **Generated-system dossier (the R→Q link)** — build it in S, or keep deferring? | **Build it in S** — a generated member has no other writeup path; it's the natural home and unblocks the export. (Pure composition, no re-analysis.) |
| D7 | **Nav placement** — new top-level "Projects" category vs under "Reports"? | **New top-level "Projects"** category (it's a workspace, not a report; export lives inside it). |

## 11. Success criteria (S)

A worldbuilder can create named projects, add real (looked-up) and procedurally-generated systems
with freeform notes, reopen any member later (generated ones re-creating **byte-identically** from
their stored spec), and **export an entire project as one multi-system dossier** (real members via Q,
generated members via the new R→Q generated-system dossier). Projects persist across sessions in two
additive, not-auto-seeded tables; `query.py project-list`/`project-get` let the sibling repo drive a
whole setting read-only; mutations stay GUI-only; the generated-member determinism contract holds
(add→reopen→export are all deep-equal to the original generation). **No existing behaviour changes**
(additive tables + nav category + ≤1 button per touched panel); suite green (offscreen, 3 live-net
baseline). **Phase S completes the planned roadmap (A–S; J declined).**
