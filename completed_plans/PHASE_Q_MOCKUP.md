## 2. The return envelope (`build_system_dossier(...)` result dict)

The document above is one field of the returned dict. `query.py dossier` would, by
default, print **the document** to stdout (it's the useful artifact); `--fmt json`
prints the whole envelope:

```json
{
  "star": "Tau Ceti",
  "fmt": "markdown",
  "sections": ["identity", "regions", "habitable_zone", "planets", "hypatia", "gcns"],
  "warnings": [],
  "document": "# Tau Ceti — System Dossier\n\n*Generated by …*\n\n## Identity\n…"
}
```

### Warnings model (the key robustness behavior)

Per-source failures degrade to **warnings**, never errors — the dossier still renders.
Example for a star with no HWC planets and no Hypatia record (e.g. a bare M-dwarf):

```json
{
  "star": "Wolf 359",
  "fmt": "markdown",
  "sections": ["identity", "regions", "habitable_zone", "gcns"],
  "warnings": [
    "planets: no NASA Exoplanet Archive or Habitable Worlds Catalog entry for this star — section omitted.",
    "hypatia: Hypatia Catalog returned no record for this star — section omitted."
  ],
  "document": "# Wolf 359 — System Dossier\n…"
}
```

A section that the reader hard-fails by design also becomes a warning rather than
aborting — e.g. a white dwarf (`compute_star_system_regions_from_simbad` returns early
for a non-OBAFGKM type):

```json
"warnings": ["regions: spectral type 'DA' has no main-sequence class — regions/HZ sections omitted."]
```

Only a total failure (the SIMBAD lookup itself errors / no such star) returns
`{"error": "..."}` with exit 1.

## 3. HTML and JSON formats

- **`--fmt json`** — **(locked: structured data only)** `document` is replaced by a
  structured `data` block (the merged section dicts) so a downstream program consumes
  fields directly instead of parsing rendered text. No rendered markdown string is emitted
  in JSON mode.

- **`--fmt html`** — same content, wrapped in a self-contained page (inline `<style>`,
  no external assets), tables mirroring the columns above.

### Format decision (locked: option A — GUI-only images)

The HTML mock above is **text-and-tables only**, which is exactly the `core/report.py` +
`query.py` output. Embedding the existing diagrams can't happen in `core/` because the
drawing helpers (`make_hz_canvas`, `make_abundance_canvas`, …) live in
`gui/visualizations/` and return **Qt** widgets, while `core/report.py` must stay Qt-free.

**Resolved:** `core/report.py` and `query.py dossier --fmt html` stay text/tables. The
`DossierExportPanel` enriches *only its own* preview/save by rendering the Qt canvases →
`figure.savefig(buf, format="png")` → base64 `<img>` spliced into the document. Clean
core↔Qt boundary. Consequence to accept: **`query.py dossier --fmt html` carries no
figures** — the downstream repo gets a complete text+table writeup, images are a
GUI-only nicety.

*(Rejected: option B, a pure-Agg render path in core — more work, refactors drawing out
of the Qt layer; revisit only if the downstream repo later needs figures in JSON/HTML.)*

## 4. Sol / Solar System — the reference-origin special path

The downstream worldbuilding repo runs a full profile + star-system analysis on **Sol**,
so the dossier must produce **the same document for the Solar System**. But Sol is a
special case across the whole app: `"Sol"`/`"Sun"` don't resolve in SIMBAD, Sol is the
distance/kinematics frame origin (not a GCNS row), and its planets are the *real* Solar
System — which NASA pscomppars and HWC don't carry. So `build_system_dossier` detects
`star.strip().lower() in {"sol", "sun"}` (the same trigger `compute_distance_between_stars`,
`compare_stars`, and the travel calculators already use) and routes to a Sol assembly path
that maps each section to its existing Sol-special-case reader — **no new astronomy, same
document shape, fully offline (local DB + constants, no network)**:

| Section | Normal-star source | **Sol source (all already in the codebase)** |
|---|---|---|
| identity | `compute_simbad_lookup` | Hardcoded solar constants (G2V, V −26.74, distance ≡ 0 — the frame origin) |
| regions + habitable_zone | `compute_star_system_regions_from_simbad` | **`compute_sol_regions()`** (`core/regions.py`, opt 13) — returns the *same flat dict*, so the region/HZ renderers run unchanged |
| planets | NASA pscomppars + HWC | **`compute_solar_system_tables()`** (`core/science.py`, opt 11) — real planets + dwarf planets + asteroids (moons available, see note) |
| hypatia | `compute_hypatia_data` | Sun baseline (the `_sol_compare_entry()` pattern, `core/databases.py`) — every [X/H] ≡ 0.0, n=0 (definitional, Lodders 2009) |
| gcns | SIMBAD `gcns` block | **N/A** — Sol is the reference origin, not a catalog row → an informational note, not a warning |

Envelope for the Sol call (note the `sections` list omits `gcns`, and a Sol-specific note):

```bash
query.py dossier --star Sol     # fully offline; --star Sun is equivalent
```
```json
{
  "star": "Sol",
  "fmt": "markdown",
  "sections": ["identity", "regions", "habitable_zone", "planets", "hypatia"],
  "warnings": [],
  "notes": ["gcns: Sol is the reference-frame origin, not a GCNS catalog source — section not applicable."],
  "document": "# Sol — System Dossier\n…"
}
```

> **Design choices the plan inherits from this Sol path:**
> - **`notes` vs `warnings`.** The Sol path introduces an additive `notes` field for
>   *by-design* omissions (GCNS N/A), distinct from `warnings` (a source that *failed* /
>   returned nothing for a real star). Keeps "expected" and "degraded" separate. *(Plan to
>   confirm: add `notes` to the envelope, or fold GCNS-N/A into `warnings`?)*
> - **Sol `sections` list omits `gcns`** rather than emitting an empty section.
> - **Sol Planets section is structurally different** (real Solar System tables, not the
>   NASA/HWC sub-tables) but lives under the same `planets` section key, so the document
>   outline is identical and the sister project parses it the same way.
> - **Moons gated.** Available from the same reader but off by default (size); opt-in via a
>   `moons` section so the worldbuilder can pull the full satellite census when wanted.
